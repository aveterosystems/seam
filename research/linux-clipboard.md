# Background clipboard on Wayland: GNOME and KDE Plasma

Research for [#60](https://github.com/aveterosystems/seam/issues/60), part of the Linux map [#58](https://github.com/aveterosystems/seam/issues/58). Checked on 2026-11-01 against source at: KWin `master` 5b7302c, Mutter `main` 432c167 (51.1), xdg-desktop-portal `main`, xdg-desktop-portal-gnome / -kde `main`, KDE Connect `master` c944488, GSConnect `main` 61cc76b.

**Question:** can a Seam app that isn't focused (a background or tray app) see when the clipboard changes, read it, and write to it, on GNOME (Mutter) and KDE Plasma (KWin) under Wayland? What changes under Flatpak?

## Answer

| Route | GNOME (Mutter ≤ 51) | KDE Plasma (KWin) | Flatpak |
|---|---|---|---|
| `ext-data-control-v1` (Wayland protocol) | **Not supported** | **Yes**, Plasma 6.4+ | KDE: allowed through 6.8; **blocked for sandboxed apps on KWin master** (next release, presumably 6.9) |
| `zwlr-data-control-unstable-v1` | Not supported | Plasma 5.20 to 6.4 only; removed in 6.5 | Same as above while it existed |
| XDG Clipboard portal (part of a RemoteDesktop session) | Yes (xdg-desktop-portal-gnome 45+) | Yes (xdg-desktop-portal-kde 6.4+) | Yes: this is the route built for sandboxes |
| GNOME Shell extension (`Meta.Selection`) | Yes; this is what GSConnect does | n/a | The extension can't ship inside a Flatpak |
| Mutter's private `org.gnome.Mutter.RemoteDesktop` D-Bus API | Works with no dialog; private and unstable | n/a | Needs `--talk-name`; not realistic |
| XWayland (an X11 client) | Read and write in the background | Reads only while an X11 window is focused; can write any time | Needs `--socket=x11` |
| Plain `wl_data_device` (GTK/Qt clipboard) | Only while focused | Only while focused | Same |

Plain version:

- **KDE:** an unsandboxed app uses `ext-data-control` and works fully in the background, with no prompt. KDE Connect does exactly this. Plasma 6.4+ is required (6.5+ has only `ext`).
- **GNOME:** Mutter offers no Wayland protocol for this. The only public, sandbox-safe route is the Clipboard portal attached to a **RemoteDesktop session**. It shows the user a "remote desktop" dialog ("Allow Clipboard Access"), and GNOME Shell shows the screen-sharing indicator in the top bar for as long as the session lives. The other route is a GNOME Shell extension (GSConnect's method), which the user must install separately.
- **Flatpak:** on GNOME it changes nothing: the portal is the answer either way. On KDE, `ext-data-control` is about to be closed to sandboxed apps (KWin commit of 2026-09-14, not in any release yet), so a Flatpak Seam must use the same Clipboard portal there too.
- **Sensitive copies:** the Linux convention is a MIME type `x-kde-passwordManagerHint` whose *content* is `secret`. KeePassXC, 1Password's `arboard`, Firefox, QtPass, pwsafe and `wl-copy --sensitive` set it; Klipper, KDE Connect and GPaste respect it. There is no freedesktop standard, and nothing matches the Mac's `TransientType` or `AutoGeneratedType`.

## 1. Wayland data-control protocols

### ext-data-control-v1

- Added in **wayland-protocols 1.39** (Dec 2024), staging: [announcement](https://lists.freedesktop.org/archives/wayland-devel/2024-December/043920.html). The protocol "allows a privileged client to control data devices", i.e. to act as a clipboard manager: get notified of every selection change, read any offer, and set the selection with no focus or input serial ([wayland.app](https://wayland.app/protocols/ext-data-control-v1)). How "privileged" is enforced is up to each compositor.
- The [wayland.app compositor table](https://wayland.app/protocols/ext-data-control-v1) lists KWin 6.7 as supporting it and **Mutter 51 as not**.

### wlr-data-control-unstable-v1

- Deprecated in favour of `ext-data-control-v1` ([wayland.app](https://wayland.app/protocols/wlr-data-control-unstable-v1)). wlroots compositors (Sway, Hyprland, etc.) still have it; KWin and Mutter do not today.

### KWin (Plasma) history, from KWin/KWayland-server source

- `wlr-data-control` added 2020-05-26 in kwayland-server ([d8b553e7](https://invent.kde.org/plasma/kwayland-server/-/commit/d8b553e71a)); first tag v5.19.90, so **Plasma 5.20**. v2 in 2021 ([6ba9856a](https://invent.kde.org/plasma/kwin/-/commit/6ba9856a29)).
- Ported to `ext-data-control` 2025-04-12 ([78c5e546](https://invent.kde.org/plasma/kwin/-/commit/78c5e54619)), first tag v6.3.90, so **Plasma 6.4**. Plasma 6.4 served both protocols from one implementation ([5f4d70be](https://invent.kde.org/plasma/kwin/-/commit/5f4d70beef)).
- `wlr-data-control` dropped 2025-05-15 ([764b7230](https://invent.kde.org/plasma/kwin/-/commit/764b7230be)), first tag v6.4.90, so **Plasma 6.5+ is `ext` only**.
- **Sandbox restriction:** [f2964e5c](https://invent.kde.org/plasma/kwin/-/commit/f2964e5c37a7144513b3e48ce5f92b15ba41fe30) (David Edmundson, 2026-09-14) adds `ext_data_control_manager_v1` to `restrictedInterfaces` in `src/wayland_server.cpp`. Restricted globals are hidden from clients where `isSandboxed()` is true. That's a client that came through `wp_security_context_v1`, or whose systemd user unit starts `app-flatpak-` or `snap.` (`src/wayland/clientconnection.cpp`, cgroup check added in [97b5274a](https://invent.kde.org/plasma/kwin/-/commit/97b5274a4f45dc5801da15231a9dfd7c682298c2), Plasma 6.8). The commit message says that before this, "we allowed ext_data_control everywhere". As of 2026-11-01 it's on `master` only, with no tag (latest is v6.8.2); **which release ships it is unverified** (likely 6.9).
- Unsandboxed clients still get it with no prompt and no indicator.

### Mutter (GNOME)

- No data-control implementation in `src/wayland/` at Mutter 51.1 (grep of source). Requests were closed: [mutter#3941 "Support ext-data-control"](https://gitlab.gnome.org/GNOME/mutter/-/issues/3941) (opened and closed 2025-02-28), [#4333 "add support zwlr_data_control_manager_v1"](https://gitlab.gnome.org/GNOME/mutter/-/issues/4333) (closed 2025-09), [#1602 "Third-party clipboard managers support on wayland"](https://gitlab.gnome.org/GNOME/mutter/-/issues/1602) (closed 2021). **Unverified:** the maintainers' stated reasons. The comment threads need a GitLab login, which this research didn't have.
- Plain Wayland clipboard needs focus: `data_device_set_selection` rejects any client that isn't `data_device->focus_client` (`src/wayland/meta-wayland-data-device.c`), and selection offers go only to the focused client.
- Open MR [!5388 "Add explicit paste destinations for history UIs"](https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/5388) (2026-10) touches clipboard-history UIs. Not merged, and its scope is unverified.

## 2. XDG Clipboard portal

- Spec: [`org.freedesktop.portal.Clipboard`](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Clipboard.html), version 1. It **creates no session of its own**: it extends a **RemoteDesktop** session (and, since xdg-desktop-portal 1.21.1, an **InputCapture** session, only while that capture is active; [NEWS](https://github.com/flatpak/xdg-desktop-portal/blob/main/NEWS.md)). Introduced in xdg-desktop-portal **1.17.0**, so the first stable release is 1.18.0 (NEWS).
- Flow: `RemoteDesktop.CreateSession`, then `SelectDevices`, then `Clipboard.RequestClipboard(session)` (**must be before Start**), then `RemoteDesktop.Start`. That shows the user a dialog, and the response carries `clipboard_enabled`. After that:
  - `SelectionOwnerChanged(session, {mime_types, session_is_owner})` fires on every clipboard change, focused or not.
  - `SelectionRead(session, mime)` returns an fd with the data.
  - Writing is `SetSelection(session, {mime_types})`, then answering each `SelectionTransfer(session, mime, serial)` with `SelectionWrite` + `SelectionWriteDone`.
- Persistence: [RemoteDesktop](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) v2 has `persist_mode` (2 = until revoked) and a single-use `restore_token` returned from `Start`. A restored session skips the dialog. GNOME's backend has supported restore since 45 ("Implement restoration of remote desktop sessions"); KDE's `remotedesktop.cpp` handles `persist_mode`/restore data.
- **Unverified:** whether `SelectDevices` with `types = 0` (no keyboard/pointer, clipboard only) is accepted by each backend. The spec only says the default is "all". The dialog's wording if a restore token is used for a clipboard-only session was also not tested.

### GNOME backend

- [xdg-desktop-portal-gnome](https://gitlab.gnome.org/GNOME/xdg-desktop-portal-gnome) **45.beta**: "Implement the Clipboard portal" (NEWS). Its `remotedesktopdialog.ui` has an "Allow _Clipboard Access" switch, shown when the app requested the clipboard. In 50.0 the Clipboard portal returns errors instead of silently succeeding.
- It proxies to Mutter's `org.gnome.Mutter.RemoteDesktop` session clipboard (`EnableClipboard`, `SelectionRead`, …). Mutter 50 split that into a separate `org.gnome.Mutter.Clipboard` interface usable from InputCapture too ([!4767](https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/4767), merged 2025-11).
- **Visible cost:** every RemoteDesktop session calls `meta_remote_access_controller_notify_new_handle` (`src/backends/meta-remote-desktop-session.c`). GNOME Shell's `ScreenSharingIndicator` (`js/ui/status/remoteAccess.js`) shows the screen-sharing pill in the top bar for any non-recording handle. So a Seam that keeps a portal session open would show GNOME's "your screen is being shared" indicator permanently. (This is inferred from source; not observed on a machine.)

### KDE backend

- [xdg-desktop-portal-kde](https://invent.kde.org/plasma/xdg-desktop-portal-kde) "Implement the clipboard portal" ([2de83ee0](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/commit/2de83ee0e0349cac3447ff3be1e05e53cf9e6246), 2025-03-26), first tag v6.3.90, so **Plasma 6.4**. `src/clipboard.cpp` is built on `ext-data-control` itself, and `data/kde.portal` lists `org.freedesktop.impl.portal.Clipboard`.
- **Unverified:** whether Plasma shows a persistent indicator during a RemoteDesktop session.

## 3. Mutter's private D-Bus API (unsandboxed GNOME)

`org.gnome.Mutter.RemoteDesktop.CreateSession` has no caller allowlist or dialog in Mutter (`src/backends/meta-remote-desktop.c`, `meta-dbus-session-manager.c` only record the sender), so an unsandboxed app could open a session and use `EnableClipboard`/`SelectionRead`/`SetSelection` directly. It is GNOME-private and versioned by Mutter, and it also triggers the screen-sharing indicator (same handle path as above). Not recommended; noted for completeness.

## 4. GNOME Shell extension route

- GSConnect (`src/shell/clipboard.js`) runs inside the shell. It connects to `global.display.get_selection()` `owner-changed` and exports its own D-Bus service `org.gnome.Shell.Extensions.GSConnect.Clipboard` (`GetMimetypes`, `GetText`, `SetText`, `GetValue`, `SetValue`, signal `OwnerChange`). Its comment says this exists because "GtkClipboard doesn't work in the background" on Wayland. The GSConnect service (a separate process) talks to it over the session bus.
- GSConnect also has `src/wl_clipboard.js`, a fallback that shells out to `wl-paste --watch` / `wl-copy`. That needs data-control, so it works on wlroots/KDE, not Mutter.
- Costs for Seam: a second deliverable (JavaScript, per-GNOME-version `shell-version` compatibility, extensions.gnome.org review), and the user must install and enable it. The D-Bus name is open to any session-bus client, so Seam would need its own access check (**not analysed here**). A Flatpak cannot install it, but a Flatpak Seam could still talk to it with a `--talk-name` permission.

## 5. XWayland fallback

- **Mutter:** when a Wayland client owns the clipboard, Mutter claims the X `CLIPBOARD` on its own window "so X11 apps can interface with it" (`src/x11/meta-x11-selection.c`), with no focus check. An X11 client's `XSetSelectionOwner` is picked up via XFixes and becomes the global owner, also without a focus check. So an X11 client (e.g. a GTK app forced to `GDK_BACKEND=x11`) can watch, read and write in the background on GNOME. (From source; not tested on a machine.)
- **KWin:** `src/xwayland/clipboard.cpp`: "If the selection is owned by a Wayland client, X11 clients can access it only when they are focused" (`x11ClientsCanAccessSelection()` is true only when the active window is an `X11Window`). X11-owned selections are forwarded to Wayland at any time. So on KDE, XWayland gives background **write** but not background **read**.
- Flatpak: needs `--socket=x11` (not `fallback-x11`, which drops X when Wayland is available). That gives up the sandbox's X isolation and goes against the "X11 where it's cheap, never promised" note in #58.

## 6. What KDE Connect and GSConnect do today

- **KDE Connect** (`plugins/clipboard/clipboardlistener.cpp`) uses `KSystemClipboard` from KGuiAddons. `KSystemClipboard::instance()` tries `WaylandClipboard` (`ext-data-control`), then `WlrWaylandClipboard` (`wlr-data-control`), then falls back to `QtClipboard` (`kguiaddons/src/systemclipboard/ksystemclipboard.cpp`). On KDE it works in the background. **On GNOME it falls back to QClipboard, which only sees changes while KDE Connect has focus** (inferred from the code path plus Mutter's focus rule above). KDE Connect doesn't use the Clipboard portal (no reference in its source).
- **GSConnect:** the shell extension above.

## 7. Marking a copy as sensitive

- De facto convention: an extra MIME type **`x-kde-passwordManagerHint`** whose data is **`secret`**. There's no freedesktop spec (none found).
  - Setters: KeePassXC `src/gui/Clipboard.cpp` (on non-Mac Unix, beside the Mac's `application/x-nspasteboard-concealed-type` and Windows' `ExcludeClipboardContentFromMonitorProcessing`); 1Password's [arboard](https://github.com/1Password/arboard/blob/master/src/platform/linux/mod.rs) (`exclude_from_history()`); Firefox `widget/gtk/nsClipboard.cpp`; `wl-copy --sensitive` ([wl-clipboard](https://github.com/bugaevc/wl-clipboard/blob/master/src/types/copy-action.c)); QtPass and pwsafe, per a GitHub code search.
  - Readers: Klipper (`klipper/historymodel.cpp`) skips history; KDE Connect marks the clip as a password and skips it only if the user turned off "send passwords" (`sendPassword`, default **true**); GPaste matches `secret`, trimming a trailing NUL or whitespace ([gpaste-sensitive-mime.c](https://github.com/Keruspe/GPaste/blob/master/src/libgpaste/gpaste-daemon/gpaste-sensitive-mime.c)).
- Mac mapping (`apps/mac/Packages/SeamSession/Sources/SeamSession/ClipRules.swift` skips `org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType`): on Linux only **Concealed** has an equivalent. Seam should treat an offer listing `x-kde-passwordManagerHint` as private.
- The hint is data, not just a type name, so checking it costs one extra read of the hint MIME type. A cheap, safe rule: treat an offer as private if it lists the type at all, and only read it to allow `public`. KDE's own tests also use `public`.

## What this means for the Linux app (input to #58, not a decision)

- KDE: `ext-data-control` (unsandboxed) or the Clipboard portal (Flatpak, from the next Plasma release). Both work in the background.
- GNOME: the Clipboard portal is the only supported route, and it brings a "remote desktop" consent dialog plus a permanent screen-sharing indicator. Otherwise, a companion Shell extension. If the indicator is unacceptable, GNOME clipboard sync may need decision 0011's "Not available on this computer", or a "turn on with the extension" setup step, in the role of the Mac's automatic-clipboard setup dialog.
- Needs a real machine: the indicator behaviour, clipboard-only device types, and restore-token prompts on both desktops.
